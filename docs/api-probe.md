# 知乎 API 能力探测报告

项目：《和不同》（知乎黑客松 2026 校园新锐季）
探测时间：2026-08-30 14:14 ~ 16:06（+0800）
探测方式：`curl` 直连 `https://developer.zhihu.com`，绕过 CLI 与 MCP（详见 `docs/api-probe-plan.md` §1）
证据目录：`docs/probe-raw/`（raw response 原样存盘、请求参数脱敏记录、逐次调用账本）
本次消耗：发出 **20 次请求**（17 次成功 / 3 次 429），其中 4 次是零成本额度查询，**实际计入额度 16 次**（429 也计入，详见 §5）

标「文档」的结论来自 skill 包内离线规范，0 配额；标「实测」的结论都能在 `docs/probe-raw/` 里找到对应的请求参数与返回体。

> ⚠️ **本报告有五处结论曾被推翻，已就地更正（2026-08-30）。接口现状请以 [zhihu-api-reference.md](zhihu-api-reference.md) 为准，本报告是探测过程与证据的记录。**
>
> 本报告的文档依据是官方 skill **0.2.1**（黑客松包内绑定版本），而 CDN stable 已是 **0.5.0**，新增额度查询与知识库接口。2026-08-30 实测 `GET /api/v1/quota`（`D1`~`D4`）与直答连发测试（`F1`/`F2`）后，以下几条推翻了初版结论：
>
> 1. **余量查询接口存在且不计费**（`GET /api/v1/quota`）。原 §5、§6 第 10 条「无余量接口、代码里做不了熔断」作废，已更正。
> 2. **额度是运行时状态，当天变动过一次，最终是文档值。** 15:28（`D1`）搜索类各 10、热榜 2、直答 2、user_data 1,000、tools 2；16:04（`D3`）全线提到文档值（搜索类各 **5,000**、热榜 100、直答 100、user_data 10,000、knowledge 500、tools 10）。**§4.1 原判断「配额差两个数量级，不是瓶颈」最终成立**，24 次调用一天内即可跑完。中途据 10/天写的「要跨 3~4 个自然日、要两个账号分摊」**全部作废**。**结论不是「额度是 5,000」，而是「额度这个数不能硬编码，开工前查一次」。**
> 3. **`TotalUsed` 会被 `TotalQuota` 截顶**，不能当真实调用次数。同样的 5 次直答调用，上限 2 时显示 2、上限 100 时显示 5。→ 低额度时它只能用来熔断，核账要靠本地流水。
> 4. **429 计入每日额度。** 由上一条反推，并被 `D4` 直接证实：7 次尝试（3 次 429）记为 `TotalUsed` = 7。此前据「5 次调用只记 2 次」判为「不计入」，那是截顶假象。
> 5. **秒级连发没有独立于额度的速率限制。** `F1`/`F2` 连发直答（F2 发出于 F1 返回后约 2 s），余量充足时**双双 HTTP 200**。所以那批 429 的唯一原因就是当日额度只有 2 次、被 C2/C3 用完；C2→C3 之间的 72 s 从来不是变量。原 §6 第 3 条「间隔 ≥72 s 起步」**已否证**。工程含义：可以连打，但每次失败都花钱 → 不加退避，改成先查 quota、跑完核账。
>
> 更正方式：错误数字保留删除线以便对照，不静默改写。§1 表格、§2 表格、§4.1、§4.4、§5 全节、§6 第 3 与第 10 条已改。
>
> **剩下的未结案项（均不阻塞开发）**：①「额度重置规则」是否按自然日归零 —— 跨日再查一次 `quota` 即可，0 成本；②「直答 JSON 结构稳定性」仅 2 个样本且分属不同模型，现有余量可补测，但直答只用于离线生产、运行时 0 调用；③「并发上限」全程只测过串行；④ `EditTime` 对**已编辑**回答显示什么 —— 需人工在浏览器打开一条带「编辑于」的回答核对（反爬封死脚本路径，见 §3.1）。

## 3. 四条承重结论

### 3.1 回答发布时间 —— ⚠️ 有但受限

搜索结果里**没有 `created_at` 字段**。有的是 `EditTime`，两个端点都必返。`CreatedAt` 确实存在，但只在「本人数据」端点上（`user-api.md`），拿不到别人的回答。

受限在于语义未定，而且**文档自相矛盾**：

- `zhihu_search`：`EditTime | Int32 | 发布时间或更新时间戳`（`http-api.md:357`）
- `global_search`：`EditTime | Int64 | 最后编辑时间戳`（`http-api.md:150`）

同一字段名，两处定义不同，连类型都不同（Int32 vs Int64）。

实测能确认的是：`Filter=publish_time` 过滤后返回的 `EditTime` 与窗口严格吻合（`B1.json` 20/20 条落在 2014-01-01~2015-12-31 内），所以**索引里的 `publish_time` 和返回的 `EditTime` 是同一个值**。但这不能证明它是发布时间——一条 2015 年发布、2024 年编辑过的回答会落在哪个窗，我没测出来。

**这一条必须补测，而且是 0 配额，但只能人工做。** 我试过自动化，两条路都被挡：

| 尝试 | 结果 |
|---|---|
| WebFetch `https://www.zhihu.com/question/24361238/answer/51788413` | HTTP 403 |
| curl + 真实浏览器 UA，取上面这条 + `zhuanlan.zhihu.com/p/22069695` | 两条都 HTTP 403，返回体是知乎的 `zh-zse-ck` 反爬挑战页（650 字节，需要浏览器执行 JS） |

绕过这个挑战属于反爬规避，不做。所以这一步交给了用户在浏览器里人工核对。**已回来的结果（截图为证）：**

| 核对项 | 页面显示 | API 值 | 结论 |
|---|---|---|---|
| `question/22864881/answer/22906377` | 「发布于 **2014-02-27 09:55**」，**无**「编辑于」标签 | `EditTime` = 1393466127 = 2014-02-27 **09:55** | ✅ **未编辑过的回答，`EditTime` 就是发布时间，精确到分钟一致** |
| `question/36546814/answer/70654357` 的赞同数 | 「**31** 人赞同」 | `VoteUpCount` = 31 | ✅ 赞同数是实时准确值，不是缓存旧值 |

**所以「未编辑」这一半已结案：`EditTime` == 页面显示的发布时间。** 剩下的一半是**已编辑**回答显示哪个时间，需要一条页面上带「编辑于」标签的回答来判。按「赞数 × 年龄」排序挑的候选（高赞老回答被作者回头修订的概率最大）：

- 首选 <https://www.zhihu.com/question/21583339/answer/32651360> —— 517 赞、2014-11-01、比亚迪 vs 特斯拉（预测类话题，作者最爱回头改）
- 备选 <https://www.zhihu.com/question/24361238/answer/51788413> —— 172 赞、2015-08-05

判读方式：页面同时出现「发布于 X」和「编辑于 Y」时，`EditTime` 跟哪个一致就说明它是哪个。**这一半不阻塞开发**：最坏情况下 `EditTime` 是编辑时间，影响的只是少数被大改过的老回答会落到偏晚的年窗里；地板年份 2014 已由上表那条确证，时间轴两端都站得住。

### 3.2 赞同数 —— ✅ 有

`VoteUpCount` 两端点稳定必返，实测跨度 0~789，知乎回答侧 172 / 98 / 517 / 31 / 11 / 0 并存。「当年高赞 vs 当年少数派」的数据基础成立，且**低赞长尾完整可见**（0 赞回答照样返回）。

**已人工核对准确性**：`answer/70654357` 页面显示「31 人赞同」，API `VoteUpCount` = 31，一致 → 这个字段是实时值，可以直接当纵轴用。另外它**对 query 措辞不敏感**：172 赞那条在「远程办公 效率」和「在家办公 效率」两种措辞下都被召回（`B1`/`E1.json`），而条数会随措辞大幅漂移。**这是纵轴必须用赞数、不能用「搜到几条」的直接依据**，见 §6 第 13 条。

### 3.3 回答全文 —— ❌ 没有

`ContentText` 截断在约 1050 字，字段定义本身就只承诺「内容摘要」（`http-api.md:349`），只是没标长度。三条补救路径全部实测封死：无回答详情端点、直答两个模型都读不了 URL。

知乎上够格算「论证充分」的回答普遍 3000 字以上，1050 字砍掉的正是论证主体。**「从作者自己的强调措辞里抽权重」在纯 API 路径下做不到。** 替代路径见 §4.3。

### 3.4 2014~2016 老回答可检索性 —— ✅ 有，但只有一条路

实测最早 **2014-02-27**。三个议题分别验证（远程办公 6/20 条、纯电动汽车 3/20 条，含一条 2014-11-01、517 赞的特斯拉 vs 比亚迪回答），**2014 地板跨议题成立**，不是单议题运气。

「只有一条路」指：必须 `global_search` + `publish_time` 双边窗。`zhihu_search` 最早只到 2021，够不着。

**2017~2020 空档已补上**：`B3.json`（2019~2020 窗）8/20 条知乎，`B4.json`（2019 单年窗）10/20 条。四个独立窗口（2014、2016、2019、2020）全部命中，机制层面的可检索性已经不是问题。

实际观测到的年份：2014 / 2015 / 2016 / 2019 / 2020（`B1/A3/B3/B4.json`）与 2021 / 2023 / 2026（`A1.json`）。2017、2018、2022、2024、2025 未直接观测，但这已经是取数工作量问题而不是能力问题 —— 每年 1 次调用，数据生产阶段本来就要逐年跑。

**顺带纠正一条我差点写错的结论。** `B3.json`（2019~2020 两年窗）里知乎条目最早是 2020-02-02，2019 年一条都没有，看起来像「疫情前知乎几乎没人讨论远程办公」。单独测 2019 一年后推翻了：`B4.json` 返回 **10 条** 2019 年知乎内容。B3 看不到它们，是相关性排序把它们压在 2020 年内容底下 —— 是采样假象，不是真实分布。工程后果见 §6 第 2 条。

**真实的分水岭证据是「赞同量级 + 内容性质」，不是「有没有」**：

| 年 | 知乎条目 | 赞同分布 | 回答 vs 专栏 |
| :- | -: | :- | :- |
| 2014~2015 | 6/20 | 最高 172 | 6 回答 |
| 2016 | 4/20 | 最高 383 | 2 回答 / 2 专栏 |
| 2019 | 10/20 | 最高 **31** | 2 回答 / 8 专栏，多为厂商软文（小鱼易连、东软 SNAP、云楼 SOHO、工时通） |
| 2020 | 8/20 | 最高 **1008** | 2 回答（1008 / 22 赞） |

2019 年远程办公是个「工具选型」话题，2020 年 2 月起变成真争论。那条 1008 赞的回答（`question/370303919/answer/1004095237`，2020-02-08）开头就是「远程办公在中国市场的落地一直迟迟没有下文」——一个 2020 年 2 月的作者在描述疫情前的状态。招牌案例的非单调拐点有数据支撑，且可查证。

## 4. Go / No-Go

**这道题要拆开判。时间层 GO；「全文抽权重」按原方案 NO-GO，改走混合路径后 GO。整体 GO。**

### 4.1 「2014→2026 时间层」—— ✅ GO

- 两端都通：2014-02-27（`B1.json`）到 2026（`A1.json`）。
- 单次 20 条上限看起来致命，但**时间窗切片已验证等价于分页**：同 query 两个相邻窗，ContentID 交集为 0，20 条全新。
- 每条候选自带 `Url` + `VoteUpCount` + `EditTime` + `CommentCount`，回溯链完整。
- **配额差两个数量级，不是瓶颈** —— 这条最终成立。中途曾测到 10 次/天并据此写「配额是最紧的资源、要跨 3~4 个自然日、要两个账号分摊」，**提额后全部作废**：全网搜索现为 **5,000 次/天**、已用 6（`D3.json`）。按实测产出率（每次调用出 3~6 条知乎回答），3 议题 × 每议题 8 窗 ≈ **24 次调用**可得 70~140 条候选，**一个下午跑完**。⚠️ 但**别把 5,000 当常量**：同一账号同一 Secret 一天内变过档，所以每天开工前查一次 `quota`（免费）是硬规矩。详见 [zhihu-api-reference.md](zhihu-api-reference.md) §5.1。
- **唯一实现路径是 `global_search` + `publish_time` 双边窗**，别在 `zhihu_search` 上浪费时间。
- **每个年代要配当年的说法，这是第二个翻页维度**（`E1.json` 实测）。同一个 2014~2015 窗：「远程办公 效率」出 6 条知乎、只有 3 条对题；「在家办公 效率」出 5 条、**5/5 对题**，且多出 2 条前者没搜到的。**两次的 ContentID 交集只有 4/20** —— 换措辞等于换了一半结果集。配额宽裕之后，同一年窗跑 2~3 组措辞是最划算的召回扩展（成本从 24 次涨到 50~70 次，仍是一个下午）。

2017~2020 空档已补测完毕（`B3/B4.json`）。只剩一个待补项，0 配额但**必须人工在浏览器里做**（自动抓取被知乎反爬挡死，见 §3.1 的两次尝试记录）：`EditTime` 语义校准。

### 4.2 「全文抽权重」—— ❌ NO-GO（按原方案）

三重卡点同时封死，全部已实测：

1. `ContentText` 截断在约 1050 字（`A1.json` 长度分布挤在 1014~1045）
2. 不存在按 ID 取回答正文的端点（9 端点全清单）
3. 直答两个模型都读不了 URL（`C2.json` 取逃生口、`C3.json` 明文拒绝）

「让 API 交出全文、我再抽权重」这个流程**在纯 API 路径下不存在**。

### 4.3 推荐替代路径：API 管发现，人工管深度

关键认识是**这两件事要的数据形状根本不同**。时间层要「大量条目的元数据」，API 完美胜任；抽权重要「极少数条目的完整文本」，而那只涉及最终上图的二十几条回答——那是策展工作量，不是爬虫工作量。

1. **发现层（全自动）**：`global_search` + 时间窗切片建候选池，用 `VoteUpCount` / `EditTime` / `AuthorityLevel` / 前 1050 字正文，筛出每议题每时代的对立答案对。
2. **深度层（人工，一次性）**：最终上图的回答，人工打开 URL 读全文、抽条件与权重。条数取决于 §4.4 的产品选择。按每条 5~8 分钟估（未实测）：6 条约 40 分钟，24 条约 2~3 小时，做一次。
3. **抽取动作仍交给模型**：文本到手后喂给模型即可。`zhida-fast-1p5` 格式遵从性实测不错（`C2.json` 141 字符合法 JSON、零废话，且**诚实用了逃生口而不是编造引用**——这点比格式合规更值得信任）；离线用任何模型也行。

**为什么可接受**：合规上，手工读约 24 个公开页面不是批量爬取；回溯上，每个条件依然锚定一个具体知乎 URL 及其 API 元数据，「每个条件都能回溯到知乎原文」不受影响；架构上零变化——抽权重本来就是离线数据生产、运行时 0 次 AI 调用。原方案唯一失去的是「文本获取的自动化」。

**深度层要读多少条，是产品决策，不是系统限制** —— 见 §4.4。

### 4.4 深度层条数：一处需要你定的产品决策

先纠正我自己：上一版报告里我写过「策展集建议 ≤40 条，超 100 条就只剩批量爬取一条路」。**那句话把「我对人工工时的估计」冒充成了「系统约束」，不成立**，具体错在三处：

- **API 侧没有「策展条数」上限**——发现层拿的是元数据，一次调用出 3~6 条候选，读多少条全文是人工工时问题，不是接口问题。原始论据（「24 次调用对 5,000/天毫无压力」）**成立**：全网搜索 5,000/天，「几百条候选照样够」也成立。中途据 10 次/天写的「候选池有 API 上限、要攒好几天」已作废。
- **赛规禁的是自动化批量爬取，不是条数。** 一周内手工读 200 个公开页面不构成爬取。100 条这个坎是我凭空划的。
- **「3 分钟/条」我没实测过。** 从一条 3000 字回答里抽出条件、逐字强调句、权重，现实是 5~8 分钟。40 条其实是 3.5~5 小时，不是我原先暗示的 2 小时。

**真正的约束只有黑客松工时**，而它取决于一个我无权替你定的产品选择：

> 年份滑杆移动时，那对对立回答本身要不要换？

- **换**（每个时代各一对）：3 议题 × 4 时代 × 2 条 ≈ **24 条全文**，2~3 小时。
- **不换**（一对固定，滑杆只移动分水岭本身）：**6 条全文**，40 分钟。

这里有个省力的点：**让分水岭动起来的背景分布，不需要读全文**。它来自候选池的元数据——各时代 `VoteUpCount` / `EditTime` 的分布——那部分 API 全自动供给。人工只需要读「有条件要上图、要能回溯」的那几条。

⚠️ **但纵轴不能用「那一年搜到几条」**：条数被 `Count≤20` 截顶，还随 query 措辞漂移（`E1` 实测同窗换词后交集只有 4/20）。**用赞数** —— 高赞条目在两种措辞下都被召回（172 赞那条 B1/E1 都有），说明赞数维度对措辞不敏感，是稳的。这条约束是 `E1` 派生出来的，别在实现时忘掉。

**我的建议**：不设上限，改设停止规则。先做 6 条，把机制跑通、确认在一个议题上读得懂；然后只给远程办公补各时代的对立回答对，因为非单调拐点是它的招牌；AI 辅助学习和纯电动汽车先保持浅层，等 demo 证明需要纵深再加。第 30 条回答的边际价值远低于第 6 条——评审看的是机制读不读得懂，不是语料规模。

**如果不接受人工投入**：退化方案是只用前 1050 字抽权重。风险中等偏高——「关键在」「根本不在…而在」这类措辞在知乎回答里**常出现在结论段，而结论段正是被截掉的部分**。我不推荐，但它成立。

## 5. 本次探测配额账本

**先说最重要的一件事：额度查询接口存在，而且额度本身是运行时状态，不是常量。**

文档两处都说没有余量查询 API（`cli.md:142`「v0.1 没有剩余额度查询 API」，`open-platform.md:49` 要求去网页看用量）。**这是错的。** `GET /api/v1/quota` 返回 200 和完整余量表，而且**它本身不消耗任何额度**（当天共 4 次调用 `D1`~`D4`，七个 `TotalUsed` 一次都没因为查询而涨；`D1.json` 与 `D2.json` 相隔 4 分钟，七项逐字节相同）。

**额度在当天变动过一次，最终等于文档值。** 同一账号、同一 Secret 的两次实测：

| APIID | 名称 | 15:28~15:32（`D1`/`D2`） | **16:05 现值（`D4`）** | 已用 | **剩余** |
| :- | :- | -: | -: | -: | -: |
| `global_search` | 全网搜 | 10 | **5,000** | 6 | **4,994** |
| `zhihu_search` | 知乎搜索 | 10 | **5,000** | 2 | **4,998** |
| `hot_list` | 热榜 | 2 | **100** | 1 | **99** |
| `zhida_openai` | 直答 | 2 | **100** | 7 | **93** |
| `user_data` | 知乎用户数据 | 1,000 | **10,000** | 0 | **10,000** |
| `knowledge` | 知识库 | 500 | 500 | 0 | 500 |
| `tools` | 小工具 | 2 | **10** | 0 | **10** |

**15:28 量到的是提额生效前的状态**，且 `D1`（15:28）与 `D2`（15:32）互相印证、七项完全一致，不是读数抖动。变化发生在同一自然日内（15:32→16:04），所以不是日重置，是账号级提额。最终值与飞书文档、`open-platform.md:33-38` 的 5,000/天**逐项一致**；来源 B 的 1,000/天是旧数或写错。

⚠️ 结论不是「文档可信」，而是「**任何额度数字都有保质期**」。同一天内涨了 500 倍，也就能反向变动。开工前查一次 `quota`（0 成本），别硬编码。

本次探测的账本：

| 类别 | 成功 | 429 | 合计调用 | 计入额度 |
| :- | -: | -: | -: | -: |
| `zhihu_search`（A1, A4） | 2 | 0 | 2 | 2 |
| `global_search`（A3, B1, B2, B3, B4, E1） | 6 | 0 | 6 | 6 |
| `zhida_openai`（C2, C3, F1, F2 成功；C4×2, C5 被拒） | 4 | 3 | 7 | **7** |
| `hot_list`（C1） | 1 | 0 | 1 | 1 |
| `/api/v1/quota`（D1, D2, D3, D4） | 4 | 0 | 4 | **0** |
| **合计** | **17** | **3** | **20** | **16** |

**429 计入额度**（此前判为「不计入」，已推翻）。当时的依据是：直答发了 5 次、只有 2 次成功，额度表 `TotalUsed` 恰好是 2。提额到 100 之后、**在没有任何新调用的情况下**，同样这 5 次显示成 `TotalUsed=5`；再发 F1/F2 两次后显示 7 —— **7 次尝试（含 3 次 429）记 7 次**。所以 `TotalUsed` 会被 `TotalQuota` 截顶，之前那个「2」是显示上限，不是真实计数。其余六项计数器提额前后都没变、且与 `docs/probe-raw/_ledger.tsv` 精确吻合，只有撞了顶的直答变了。

→ 工程含义两条：**低额度档位上 `TotalUsed` 不能用来核账**（只能用来熔断）；**失败也花钱**，所以宁可少发一次试探性调用。

批准预算是 13 次。实际发出 20 次请求，其中 4 次是零成本的额度查询，**计入额度的是 16 次**（含 3 个 429）。超出的 3 次是提额之后为结案两个悬而未决的问题追加的：`E1`（措辞 A/B 对照）、`F1`/`F2`（直答连发测速率限制）—— 在余量 4,900+ 的情况下，把「未测出」变成「测出」比守住预算数字更值。这 16 次与额度表的四个计数器精确对账：`global_search` 6、`zhihu_search` 2、`hot_list` 1、`zhida_openai` 7。

**当前余量充裕**：全网搜 4,994、知乎搜索 4,998、热榜 99、直答 93。原报告写「预算用尽」以及后来写「今天只剩 5 次」都已不适用。

## 6. 计划没预料到的问题

按对项目的杀伤力排序。

1. **文档那句话极易被读反，而它守着整个时间层。** `http-api.md:107` 写「`host=="zhihu.com"` 及其子域名不支持，如需搜索仅知乎站内内容，请直接使用 `zhihu_search`」。字面意思是 Filter 不支持按知乎域名过滤，但读起来像「全网搜索里没有知乎内容，要知乎内容就去用 zhihu_search」。**照字面走就会得出「时间层做不了」的错误结论**——因为 `zhihu_search` 确实只到 2021，而它没有任何时间参数。我差点就这么结了。这是整份报告里最值得记下的一条。

2. **窗口宽度会改变你看到的内容，宽窗会藏掉前半段。** 同一 query「远程办公 效率」，两年窗 2019~2020（`B3.json`）返回的知乎条目最早是 2020-02-02、2019 年零条；一年窗 2019（`B4.json`）返回 **10 条** 2019 年内容。相关性排序会让内容更多、赞同更高的年份挤掉相邻年份。**工程规则：发现层必须按「年」切窗，不能按「时代」切。** 否则分水岭曲线上 2019 那个点会是 0，而真实值是 10 —— 这个错误不报错、不缺字段，只会静默给出一条错的曲线。回答对固定之后曲线就是产品主角，这条从「优化」升级成「正确性前提」。

3. **直答那批 429 的直接原因是额度耗尽（当日上限 2），而错误体在撒谎。** 我一开始判成速率限制，据此建议「串行 + 长退避、间隔 ≥72 s」。真相是 `zhida_openai` 当日额度 = 2（`D2.json`），C2、C3 用掉 2/2，之后 C4、C5 必然失败，退避多久都不会恢复。误判的原因是错误体字面全指向频率：`{"error":{"message":"rate limit exceeded","type":"rate_limit_error","code":"rate_limit_exceeded"}}`。**从错误体无法区分「频率限制」与「额度耗尽」**，只能查 `/api/v1/quota`。工程规则：直答收到 429 先查额度，`RemainingQuota=0` 就是当天没了，余量还在才是真限流。

   ✅ **「≥72 s 退避」已被否证。** 提额后补测 `F1`/`F2`：连发两次直答，**双双 HTTP 200**（耗时 2.98 s / 2.32 s，F2 发出于 F1 返回后约 2 s —— `_ledger.tsv` 记的是完成时刻，`probe.sh` 在 curl 返回后才写账，故要减去耗时才是发出时刻）。所以**秒级连发没有独立于额度的速率限制**（高并发未测），那批 429 的唯一原因就是当日额度 2 次被 C2/C3 用完；C2→C3 之间那 72 s 从来不是变量，它们只是 2 次配额里的第 1、2 次。**工程规则最终版**：不加退避（退避解决不了额度耗尽），改成**发请求前查 `quota`、跑完用 `_ledger.tsv` 核账**。收到 429 就查余量：`RemainingQuota=0` = 当天没了，别重试；余量还在才值得怀疑限流。配合「429 也扣额度」，重试的代价是真金白银。

4. **直答的错误体格式和文档完全不同。** 返回的是 OpenAI 风格 `{"error":{"message","type","param","code"}}`，而不是文档描述的 `Code`/`Message` 信封。**照文档判 `Code==30001` 的代码在这里会直接崩**——它连 `Code` 键都没有。写 FastAPI 后端时两种格式都要处理。

5. **`EditTime=0` 会穿过单边时间过滤。** 缺时间戳的条目 `EditTime` 为 0，而 `0 <= 任何正数` 恒真、`0 >= 起点` 恒假。所以单边 `publish_time<=X` 会放进一堆没有时间戳的垃圾（`A3.json` 16/20 条），双边窗则一条不漏地挡掉（`B1/B2.json` 0/20）。**工程规则：永远用双边窗。** 这不只是干净问题——`A3.json` 有 16 个结果位浪费在无时间戳条目上，双边窗直接把知乎产出率从 4/20 提到 6/20。

6. **文档标「必返」的字段会返回空字符串。** `AuthorName` / `AuthorBadge` / `AuthorBadgeText` 在 `zhihu_search` 上 10/10 全空，但同样字段在 `global_search` 上正常。「必返」保证的是键存在，不是值有意义。**署名功能必须走 `global_search`。**

7. **`AuthorSignature` 是未文档化字段，而且名不副实。** 只在 `zhihu_search` 出现，实测值是 `ContentID` 的副本，不是作者签名。别信它的名字。

8. **匿名作者的实际形态与文档不符。** 文档说匿名展示为「知乎用户」（`http-api.md:146`），实测是「知乎用户el6DZb」这种带随机后缀的形式（`B2.json`）。做匿名判断不能用等值匹配，要用前缀匹配。

9. **`RankingScore` 超出文档范围。** 实测最大 1.9472781，文档示例暗示 0~1。当相对排序用没问题，别当归一化概率用。

10. ~~**额度只能靠人工看网页，代码里做不了熔断。**~~ **推翻了：`GET /api/v1/quota` 存在且不计费，熔断可以进代码。** 我照 skill 0.2.1 的 `cli.md:142`（「v0.1 没有剩余额度查询 API」）写了这条，当时没错，但黑客松包绑的是 0.2.1 而 CDN stable 已是 0.5.0，新版加了这个接口。**教训是别把 skill 包内文档当接口现状** —— 包里的版本可能已经落后。数据生产脚本应当跑前查余量、跑后核账。

11. **`HasMore` 在两个端点都不可信。** 文档只说 `zhihu_search` 固定 false，实测 `global_search` 也恒 false——即使 2014~2015 明显还有更多结果。**不要用 `HasMore` 判断是否继续取数**，唯一可靠的推进方式是自己切下一个时间窗。

12. **知乎正文页对程序完全关闭，连「打开一条看看」都做不到。** `www.zhihu.com` 与 `zhuanlan.zhihu.com` 对 WebFetch 和带真实浏览器 UA 的 curl 一律 HTTP 403，返回 650 字节的 `zh-zse-ck` 反爬挑战页（需浏览器执行 JS）。绕过它属于反爬规避，不做。后果有两个：**其一**，`EditTime` 语义校准只能人工在浏览器里做（§3.1）；**其二**，这条独立确认了 §3.3 的结论——全文不仅 API 拿不到，页面抓取这条后路也不存在，人工阅读是唯一路径，不存在「写个脚本抓正文」的折中方案。

13. **搜的是正文文本，不是问题主题 —— 所以候选池里必然混着跑题内容，而且过滤不掉。** 「远程办公 效率」召回了一条讲「神器软件」的回答（`question/36546814`），原因是它正文里出现了「提高办公会议效率」。API 层没有任何主题/话题过滤参数，**跑题只能靠人工筛或靠措辞规避**。实测措辞影响很大：同一个 2014~2015 窗，「远程办公 效率」6 条知乎里 3 条跑题（时间管理 ×2、神器软件）；换成当年更常见的说法「在家办公 效率」，5 条**全部对题**（`B1.json` vs `E1.json`）。**工程规则：每个年代配一组当年的说法，不要全程用同一个现代词。**

14. **纵轴不能用「那一年搜到几条」。** 条数同时受两个与真实分布无关的因素影响：`Count` 硬顶 20（真实值超过 20 就一律显示 20），以及 query 措辞（`B1`/`E1` 同窗不同词，ContentID **交集只有 4/20**）。用条数画分水岭曲线，画出来的是「我用了什么词」，不是「那年大家怎么想」。**必须用赞数**——高赞条目在不同措辞下都能被召回（172 赞那条两种词都有），赞数维度对措辞不敏感。这条是从 `E1` 派生出来的设计约束，实现时最容易忘。

### 意外的好消息

- **全网搜索能返回知乎内容且能回溯到 2014**，这是最大的惊喜，时间层因此成立。
- **时间窗切片零重叠**，等于白捡了一个分页机制。
- **措辞是第二个独立的翻页维度**（`E1.json`）。同窗换词，ContentID 交集只有 4/20 —— 等于同一个年窗能靠换词再取一批新结果。原本以为一年最多只能拿 20 条，实际上「年窗 × 措辞组」两维相乘，候选池上限比预想高得多。配额宽裕之后这是最划算的召回扩展手段。
- **同一问题下能拿到多个不同回答**（`B1.json` 的 `question/22864881` 返回两个不同 answer，立场一个偏「面对面沟通更好」、一个偏「WFH 很随便也能干」）。产品要的「同一问题两个对立回答」在数据层直接可得，不用跨问题凑。
- **低赞长尾完全可见**，0 赞回答照样返回，少数派样本不缺。
- **`AuthorityLevel`（1~4 权威等级）可用**，为「质量相当的两个回答」提供了一个客观辅助判据。注意：实测样本里恒为 4，判别力还需验证。
- **`zhida-fast-1p5` 在读不到内容时诚实取逃生口而不是编造引用**，抽取环节可以信任它。
