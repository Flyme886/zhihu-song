# 思想引力场：真实后端接入方案

后续实施范围已按用户决定收敛为“预设案例 + 真实取材 + 实时对谈 + 本机记录”。已完成的内容与真实调用证据见 [演示 API 接入验收](思想引力场_演示API接入验收_2026-09-11.md)。下文保留初次审计提出的完整后端选项，账号、数据库和多人能力不属于本次实施。

核查日期：2026-09-11。对象：当前 `web/` 和本机 8081 服务。本文是依据代码、运行状态、浏览器页面和官方在线文档形成的实施方案，未实施后端改造、配置凭证或发布公网。

**已有案例是产品内容资产，继续保留。真正需要补齐的是：新输入可以驱动检索、语义分析和讨论生成，结果可以按用户持久保存。** 用户手动确认关系、本地记录、粒子动画也都是真实功能；它们分别尚未具有自动语义分析、跨设备同步和真人社交能力，不能统称 mock。

**已核实的现状**

| 环节 | 当前行为 | 接入目标 |
| --- | --- | --- |
| 案例 | `web/cases/catalog.json` 有 9 题、38 个观点，包含已有知乎来源摘要和策划视角 | 作为精选案例导入内容库，保留原标识、出处、规则和彩蛋 |
| 找问题 | `loadCatalog()` 读取固定目录；侧栏搜索过滤该目录 | 支持关键词发现和粘贴知乎问题链接，创建目录外的新话题 |
| 找材料 | `zhihu_api.py` 已有搜索适配器，但只允许目录中的 topicId，并使用预先配置的查询 | 新话题也可以按问题链接或关键词获取材料 |
| 观点球 | 取摘要前 160 字作为 claim，位置来自固定布局数组 | 提炼主张、理由、条件及出处；布局消费语义结果 |
| 关系 | `relationFor()` 使用示例关系或用户确认；自由输入不自动认定赞反 | 增加有依据的关系建议，保留人工纠正和“信息不足” |
| 对谈 | 已有直答和兼容模型代理；本地模板由 `demoTurn()` 提供 | 正式讨论统一走后端会话与模型调用 |
| 讨论入口 | `chooseAgents()` 可选 provider；碰撞调用 `openDiscussion()` 时默认 `mode='demo'` | 所有入口使用同一 provider 策略，配置成功后仍需实际连通验证 |
| 整理 | `finishDiscussion()` 展示双方原主张、补充条件和固定提示 | 对实际对话提炼共同点、分歧、待验证问题，交给用户确认 |
| 我的星球 | `SessionStore` 使用 localStorage 保存观点版本、来源快照和记录 | 本地草稿继续保留，正式记录按账号保存并可跨设备恢复 |

本机实测：`/api/agent/status` 返回 `configured=false, zhihuConfigured=false`；`/api/zhihu/status` 返回 `configured=false`；robotaxi 在线缓存为 0 条。浏览器中“知乎直答”和“实时 Agent”选项均禁用，“演示对谈”被选中。这不否定目录中已有案例的有效性，只说明运行中的在线链路尚未配置。

**知乎可以提供的能力**

| 用户动作 | 官方能力 | 必须保留的边界 |
| --- | --- | --- |
| 输入关键词找相关观点 | `GET /api/v1/content/zhihu_search` | Count 最大 10，HasMore 当前固定 false；ContentText 为摘要；保留 ContentID、作者、头像、原链接及 UTM 参数。[文档](https://developer.zhihu.com/docs?key=zhihu_search) |
| 粘贴一个知乎问题 | `GET /api/v1/content/question_answers` | 传 QuestionUrl，Limit 1–50；按 Paging.NextOffset 翻页。Summary 为摘要或截取；当前文档未承诺作者昵称、头像和全文。[文档](https://developer.zhihu.com/docs?key=question_answers) |
| 围绕某个主题发现问题 | `GET /api/v1/user/question_recommendations` | 提供 Query 可按主题推荐；不传时按 Access Secret 所属用户画像推荐，不能据此承诺每位访客的个性化推荐。返回标题和链接，不返回观点关系。[文档](https://developer.zhihu.com/docs?key=question_recommendations) |
| 基于材料对话、提炼和整理 | `POST /v1/chat/completions` | 上下文模型为 zhida-fast-1p5、zhida-thinking-1p5；实际模型权限需验证。目前仅保证 model/messages/stream 三字段，不应依赖 response_format 或 tools。[文档](https://developer.zhihu.com/docs?key=zhida) |
| 知乎登录 | OAuth 授权码流程 | Access Secret、app_key、用户 access_token 分工不同。黑客松凭证按赛事流程获取，回调必须匹配。通用 API 不要求每位访客先做 OAuth。[文档](https://developer.zhihu.com/docs?key=zhihu_oauth_integrated) |
| 导入用户自己的观点素材 | `GET /api/v1/user/contents` 及关注、收藏相关接口 | 查询登录用户时须同时使用服务端 Access Secret 和对应 X-OAuth-Token。未传用户令牌会读取开发者本人数据；授权失效时必须停止，不能删去该 Header 继续调用。[文档](https://developer.zhihu.com/docs?key=user_contents) |
| 管理调用预算 | `GET /api/v1/quota` | 当前额度项包括 question_answers、creator、zhida_openai 等。按实际账户额度限制请求，不沿用旧文档里只有 7 项的清单。[文档](https://developer.zhihu.com/docs?key=quota) |

“相似观点”“有价值的分歧”“我的思想轨迹”和产品内多人会话，需要自己实现。以上公开文档未提供一套可直接使用的思想匹配、站内私信、真人在线状态或讨论房间后端。知识库可用于检索素材，不替代应用的用户、会话和记录数据库。

**建议先完成的产品闭环**

1. **用户提交问题或想法。** 保留现有精选案例入口，新增“探索新问题”。有问题链接时走问题回答接口；自由主题先搜索或主题推荐，让用户确认选中的问题。自由观点在当前议题中提炼，不强迫每次输入都新建话题。
2. **后端获取并保存材料。** 每次按预算取少量材料，去重并保存来源快照；已有案例作为精选材料参与使用，不因一次同步整体被覆盖。历史案例继续遵守自己的时间和设定，新话题不套用萝卜快跑的 2024 年限制。只有一条有效材料时展示一条，无结果时如实显示，不补造内容。
3. **生成可核对的观点卡。** 从每份材料提炼核心主张、理由、条件、待证实项；每个生成字段关联来源 ID 和支持它的短片段。用户原文单独保存，用户可以纠正提炼结果。结构化输出由应用解析和校验；不符合结构时保留原材料并标记分析失败。
4. **给出关系建议。** 比较我的观点与当前 4–8 个候选材料，分别考虑共同关切、结论、条件和证据。返回相近、分歧、不相关、信息不足及简短理由；同主题不能直接等于同立场。不强凑一正一反，人工确认覆盖建议。第一版可批量交给模型比较，无需先建设大规模向量库。
5. **碰撞进入真实讨论。** 统一所有入口的模型策略。后端从数据库读取材料与对话，前端提交会话 ID 和用户新发言；不能靠前端重新发送整段历史来定义真实会话。双方逐轮回应最新信息，主持人补充生成新的会话版本，使旧生成结果失效。发言标明 Agent 基于材料生成，不冒充原答主或另一位在线真人。
6. **整理并保存。** 模型基于实际已完成的对话生成整理草稿，列出被哪些消息支持的共同点、未解决分歧和证据缺口。用户编辑确认后保存；改变立场由用户决定。账号登录后，另一浏览器可以读取同一份记录和当时的材料版本。

一个验收例子：输入目录中没有的“AI 能否参与作文评分”，带着“我支持基础反馈，但反对机器决定最终分数”的观点进入。材料来自这次检索或可追溯缓存；关系建议能保留“基础反馈”和“最终评分”的区别；加入“教师必须复核”的条件后，后续发言回应这一条件；整理关联这次对话；换浏览器仍能找回。该例仅为验收输入，不预先规定检索一定有结果或双方一定形成共识。

**后端组织与数据归属**

建议沿用 Python 方向，把当前预览 HTTP Handler 拆成应用 API、知乎适配器、观点分析、讨论编排和数据存储五部分；前端继续使用现有页面与视觉组件。单实例黑客松版可采用 FastAPI 和持久卷上的 SQLite，先实现完整用户隔离和备份；有多实例写入需求时再切换合适的数据库。不要把 `.data/*.json` 和进程内锁当作多用户持久存储方案。

建议保留的数据对象：

- 用户与应用会话：本地用户 ID、知乎身份映射、会话有效期。OAuth 令牌仅由服务端处理。
- 话题：来源、原问题 URL、规则、时间范围、精选状态。
- 来源及版本：来源类型、内容 ID、原链接、摘要、可得的作者字段、获取时间、内容散列、搜索请求标识。
- 观点及版本：用户原文或材料提炼、sourceIds、主张与条件、用户确认状态。
- 关系：两份观点的版本、建议关系、理由、依据、用户纠正。
- 讨论、消息与整理：参与观点快照、逐条消息、生成状态、主持人补充、模型与请求 ID、用户确认的记录。
- 同步任务：缓存键、游标、预算、任务状态和错误类型。

localStorage 继续保存草稿和待同步修改；不能把“本页已保存”展示成“云端已保存”。导入现有本地记录时先展示条数和内容范围，让用户主动选择导入当前账号，避免共用电脑上的历史被自动归入错误账号。私人观点默认只用于当前产品会话；把观点转成外部搜索关键词或导入第三方知识库是不同的数据动作，应在界面清楚说明范围。

**建议的应用接口（自建接口，不是知乎官方接口）**

| 接口 | 用途 |
| --- | --- |
| `GET /api/topics` | 精选及已经创建的话题目录 |
| `POST /api/topics/discover` | 关键词或问题 URL 发现，返回候选，不自动创建所有结果 |
| `POST /api/topics` | 确认创建话题 |
| `POST /api/topics/{id}/sources/sync` | 受预算限制的材料同步，返回任务状态 |
| `POST /api/opinions` | 保存用户原文，触发提炼并返回分析状态 |
| `GET /api/opinions/{id}/relations` | 当前观点版本的关系建议 |
| `PUT /api/relations/{id}/confirmation` | 用户确认或纠正关系 |
| `POST /api/discussions` | 固定参与观点版本并创建后端会话 |
| `POST /api/discussions/{id}/messages` | 用户补充，更新会话版本 |
| `POST /api/discussions/{id}/turns` | 生成下一轮，带幂等键和期望会话版本 |
| `GET /api/discussions/{id}/events` | 可选 SSE 进度和完成事件 |
| `POST /api/discussions/{id}/summary` | 根据真实消息生成整理草稿 |
| `POST /api/records` / `GET /api/me/history` | 保存已确认记录与读取个人历史 |
| `GET /api/auth/zhihu/start` / `GET /api/auth/zhihu/callback` | OAuth 登录与应用会话建立 |

所有含用户数据的 ID 查询都检查归属。逐轮生成用数据库状态记录 in_progress/completed/failed，重复点击不能重复落库。模型调用若超时且结果未知，不自动重发 POST；返回明确状态供用户选择重试。使用 SSE 时，中途错误不能因为 HTTP 200 就被当成完成。

**具体改造位置**

- `web/zhihu_api.py`：保留已实现的服务端鉴权、重定向保护、错误收敛；补 question_answers 和按需问题发现。分别适配 ContentID/ContentText 与 ContentToken/Summary；缺作者的结果允许作者为空，不能编造署名，也不能直接被旧 normalize 丢弃。
- `web/answers.js`、`web/app.js`：目录改为后端读取，提供目录外话题入口；合并精选案例与在线来源；显示获取、分析、失败状态。
- `web/relations.js`：消费后端建议与用户纠正。弹簧、距离和碰撞仍在前端运行；它们不负责决定观点是否相似。
- `web/relationship-ui.js`：去掉正式流程对默认 demo 的依赖；统一入口，使用后端会话；让整理消费实际消息。离线演练可保留为用户明确选择的模式，在线失败不静默切成模板发言。
- `web/server.py`：从一次性请求转发升级为有用户、来源、会话、归属校验和持久状态的应用服务。状态接口区分 configured、lastVerifiedAt、最近错误，分别报告搜索和直答能力。
- `web/session.js`、`web/history.js`：保留草稿、恢复和导出，增加账号同步；观点与来源的旧版本不被最新材料覆盖。

**实施顺序**

1. 接真实直答，修复所有入口的 provider 选择，并把讨论和记录存到服务端。已有案例即可用来完成这一阶段，先打通最短链路。
2. 接任意问题 URL 和主题检索；补材料规范化、观点提炼和关系建议。完成一个目录外的新问题闭环。
3. 接知乎 OAuth、跨设备历史和用户主动导入的个人内容。公共内容体验可先用服务端访客会话开发，不必被 OAuth 凭证准备阻断；导入他人数据则必须等用户授权。
4. 增加主题推荐、实时热榜或知识库检索。真人匹配与多人房间作为独立产品增量，在参与者明确同意后再建设。

前两阶段完成后，产品即可真实支持“已有案例 + 新问题 + 实时 AI 讨论”；第三阶段完成后，“我的星球”才具备稳定账号身份和跨设备轨迹。真人社交仍需单独验证，不能由 OAuth 登录或 Agent 对谈推导出来。

**验收与本次验证限制**

- 实际输入目录外问题，后端保存新 topicId 和真实来源；没有结果可以合理结束，不显示假成功。
- 随机抽取观点卡，能打开对应来源；摘要、策划文字和 AI 提炼字段清楚区分。
- 同一材料下修订自己的条件，关系建议应重新计算；旧版本的建议不可直接套用。
- 从碰撞、详情和 Agent 选择器分别发起讨论，验证真实模型请求与实际返回，并检查主持人临时补充确实进入上下文。
- 断网、鉴权失败、额度不足、空摘要和流式中断时保留已有材料，明确显示受影响环节，不返回模板冒充在线生成。
- 模型整理只引用已完成消息；用户确认前不自动宣称双方达成共识。
- 两个账号彼此看不到私人记录；同一账号在另一浏览器可恢复。重启服务后记录与来源快照仍在。
- 页面重开不重复请求上游；并发双击不重复生成或保存；额度受限后不持续轮询。

本次只读页面检查和官方文档核验完成；Python 现有 7 项测试通过，但其上游使用本地测试替身，并非真实知乎验收。执行 JavaScript 测试当时为 20 通过、2 失败：缺少 `formation.js`，以及 `nearestUnconfirmed` 尚不可调用。工作区在核查过程中出现新增测试文件，以上是当时快照，不推断其他任务的最终状态。本次未修改这些实现。

真实知乎搜索、问题回答、直答和 OAuth 尚未完成端到端验收。下一步实施需要部署环境中的 Access Secret；账号登录另需黑客松 app_id、app_key 和登记回调。凭证在安全配置处设置，不进入前端、仓库或报告。
